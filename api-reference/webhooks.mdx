Versive can send an HTTPS webhook when an interview is completed, a participant is screened out, or a study's quota
fills. Webhooks are an organization-level integration, and organization owners and admins set them up themselves.

## Set up webhooks

1. Go to **Organization → Connectors** and open **Webhooks**.
2. Select **Set up webhooks**.
3. Select **Manage endpoints** to open the webhooks portal in a new tab. There you can add one or more HTTPS
   endpoints, choose which events each endpoint receives, see delivery logs, replay messages, and rotate signing secrets.

The portal link expires after one hour. Open the **Webhooks** panel again to get a new one (a panel left open refreshes it on its own). Turning webhooks off
stops deliveries but keeps your endpoints, so they are used again when you turn webhooks back on. Events that happen
while webhooks are off are not sent later. Creating and rotating destinations is not part of the public `v1` REST
API.

## Events

| Event | Sent when |
| --- | --- |
| `interview.completed` | A participant completes an interview. |
| `interview.screened_out` | A participant is screened out of an interview. |
| `study.quota_filled` | A study's [quota](/studies/settings#quotas) is full. |

If the Versive team set up your webhooks before self-serve setup, you receive `interview.screened_out` and
`study.quota_filled` only after an owner or admin turns webhooks off and back on in
**Organization → Connectors → Webhooks**. Until then you receive `interview.completed` only. An endpoint with no event
filter receives every event type, so if your receiver doesn't check `event_type`, subscribe that endpoint to
`interview.completed` only in the portal before you turn webhooks back on.

### `interview.completed`

The HTTP request body contains the event type and the completed interview and study:

```json
{
  "event_type": "interview.completed",
  "interview": {
    "id": "interview-uuid",
    "status": "closed",
    "vid": "participant-facing-id",
    "used_fallback_transcription": false
  },
  "study": {
    "id": "study-uuid",
    "title": "Onboarding research"
  }
}
```

The interview payload can include transcript, recording, timing, and metadata fields. Treat the entire request as
sensitive research data, log only the fields you need, and do not expose the destination publicly.

`interview.used_fallback_transcription` is `true` if any of the interview's recorded answers was transcribed by a
fallback model rather than one of Versive's primary transcription models. It is `false` when only primary models
were used, or when no transcription was recorded. An attempt that fails and then succeeds on another primary model
does not set the flag, and transcribing an answer again later does not clear it. Text generation and speech synthesis
do not affect the flag. Real-time voice interviews transcribe speech live on a separate path, so the flag is always
`false` for them.

### `interview.screened_out`

A slim payload with identifiers, status, timestamps and the interview metadata. It never includes the transcript,
conversation or recording.

```json
{
  "event_type": "interview.screened_out",
  "version": 1,
  "interview": {
    "id": "interview-uuid",
    "status": "screened_out",
    "vid": "participant-facing-id",
    "is_mock": false,
    "created_at": "2026-10-20T10:00:00.000Z",
    "completed_at": "2026-10-20T10:05:00.000Z",
    "metadata": {}
  },
  "study": {
    "id": "study-uuid",
    "title": "Onboarding research"
  }
}
```

### `study.quota_filled`

Sent once when a study reaches its quota: its total cap, or, with a cap per link parameter value, when every value is
full. It arrives after the `interview.completed` events of the interviews it counts. Archived interviews and
interviews that finish after the quota filled don't send it again. If you raise the quota and the study fills again,
you get a new event for the new limit. Only a completed interview triggers the event: lowering a quota to the number
of completes the study already has doesn't send it.

`quota.mode` is `fixed` for a total cap or `url_param` for caps per link parameter value; with `url_param`, `limit` and
`complete` are totals across all values. `complete` can exceed `limit` when several participants finish at the same
time. [Question quotas](/studies/question-quotas) and [quota cells](/studies/quota-cells) don't send this event. To read the counts at any time, use
[Get quota progress](/api-reference/quotas/get-quota-progress).

```json
{
  "event_type": "study.quota_filled",
  "version": 1,
  "study": {
    "id": "study-uuid",
    "title": "Onboarding research"
  },
  "quota": {
    "mode": "fixed",
    "limit": 100,
    "complete": 100
  },
  "filled_at": "2026-12-01T10:05:00.000000+00:00"
}
```

## Verify every request

Deliveries are signed by Svix. Verify the `svix-id`, `svix-timestamp`, and `svix-signature` headers against your endpoint
secret before parsing or processing the payload. Use a maintained Svix library when one is available for your language,
reject stale timestamps, and preserve the raw request body for signature verification.

See the [Svix verification guide](https://docs.svix.com/receiving/verifying-payloads/how) for language-specific examples.

## Retries and idempotency

Return a `2xx` response only after your service has accepted the event. Use the `svix-id` header as an idempotency key
because a delivery may be retried. Queue slow work and respond promptly rather than performing long-running processing
in the request handler. If Svix is unreachable, Versive retries handing an event to Svix for about 10 hours.

For changes to available events or webhook management, follow the
[versioning policy](/api-reference/versioning).
